## 1. 需求理解与覆盖情况

招标原文的核心诉求是「公共电脑上，用户自己上传文件、自己付费、机器自己出纸」。系统由三部分组成：**面向用户的 Web 端**、**跑在公共电脑上的打印助手**、**串联两者的后端与支付渠道**。

需求逐条覆盖如下：

| 招标要求 | 实现方式 | 代码位置 |
|---|---|---|
| 公共电脑、手机号登录 | 手机号 + 短信验证码；会话存库、无操作 15 分钟自动登出、可远程吊销 | `service/AuthService`、`auth/SessionService`、`App.vue` 空闲计时 |
| 上传 Word/Excel/PDF/图片，选份数、彩色/黑白、单双面 | 上传即服务端转 PDF，页数、金额服务端计算，前端不可改价 | `service/FileService`、`service/DocumentConverter`、`service/PriceCalculator` |
| 微信/支付宝扫码付款，**真实调用支付流程** | 支付宝当面付 `alipay.trade.precreate`；微信 APIv3 Native 下单；回调 RSA2 / SHA256-RSA2048 验签 | `pay/AlipayGateway`、`pay/WechatGateway`、`controller/PayNotifyController` |
| 付款成功打印机自动出纸 | 支付入账后建打印任务，助手按终端轮询领取并打印，回查系统打印队列确认结果 | `service/PaymentService`、`service/PrintTaskService`、`print-agent/` |
| Vue 前端 / Java 后端 / .NET 打印辅助 | 完全按指定技术栈实现，无额外框架替换 | `frontend/`、`backend/`、`print-agent/` |
| Git / Nginx / Linux 配置 | 仓库含 `.gitignore` 与完整提交历史；`deploy/nginx.conf`、systemd unit、docker-compose、一键安装脚本 | `deploy/` |
| 可运行系统、源码、详细设计文档、测试报告 | 四件套齐备；另附冒烟/攻击复测脚本与执行结果 | `README.md`、`docs/`、`scripts/smoke_test.py` |

**关于「真实调用支付流程」**：系统默认 `PAY_MOCK_ENABLED=false`，此时不存在任何可绕过扣款的接口。填入商户参数后即为线上真实收款；未填参数时后端会明确拒绝下单支付（返回"渠道未配置"），**不会静默降级为假支付**。模拟支付仅在 `demo` profile 下显式开启。

## 2. 总体架构

### 2.1 部署拓扑

```
                 ┌──────────────────────────── 园区内网 ────────────────────────────┐
                 │                                                                  │
  用户浏览器 ──HTTPS──▶ Nginx ──┬── /             → 前端静态资源（SPA）              │
  （公共电脑）                  └── /api/          → Spring Boot :8080（仅内网监听） │
                 │                                    │                             │
                 │                                    ├── MySQL 8（订单/任务/审计） │
                 │                                    ├── 本地磁盘（上传文件）      │
                 │                                    └── 支付宝 / 微信支付（出网） │
                 │                                                                  │
                 │   打印电脑：PrintAgent（.NET 8）──X-Agent-Token──▶ 后端 /api/agent │
                 │                └── SumatraPDF / CUPS ──▶ 物理打印机                │
                 └──────────────────────────────────────────────────────────────────┘
```

要点：

- 后端**不直接对外暴露**，只监听 127.0.0.1 或内网地址，由 Nginx 终止 TLS 并反代。
- 打印助手是**出站轮询**模型，不需要公网可达，也不需要开放任何入站端口，园区防火墙策略最小。
- 支付回调要求后端能被支付宝/微信访问，因此 `PUBLIC_BASE_URL` 必须是公网可达的 HTTPS 域名。

### 2.2 选型理由

| 组件 | 选择 | 理由 |
|---|---|---|
| 后端 | Spring Boot 3.2 + JPA | 招标指定 Java；JPA 便于用 `@Lock` / 条件更新表达并发语义 |
| 数据库 | MySQL 8（InnoDB） | 行锁与唯一索引是"防重复入账/防重复领取"的基础；生产已有运维经验 |
| 前端 | Vue 3 + Vite + Element Plus | 招标指定 Vue；Element Plus 提供现成的表格/表单/消息组件，符合公共终端"大字号、少层级"的界面要求 |
| 打印助手 | .NET 8 控制台 + Win32 Spooler P/Invoke | 招标指定 .NET；直接读打印队列才能拿到"是否真的出纸"，而不是只看命令退出码 |
| 文档转换 | LibreOffice headless | word/excel/ppt 的页数只有真正渲染才准确；PDF/图片直接用 PDFBox 计数 |
| 反向代理 | Nginx | 招标指定；同时承担静态资源、TLS、上传大小与超时控制 |

### 2.3 后端分层

```
controller/   HTTP 契约层：参数校验、鉴权上下文、DTO 转换
service/      业务编排层：事务边界、状态机流转、跨渠道编排
pay/          支付渠道适配层：PaymentGateway 接口 + 支付宝/微信实现
repo/         数据访问层：JPA Repository，含行锁与条件更新语句
entity/       领域实体（含状态枚举）
job/          定时任务：订单超时关单、任务超时回收、文件到期清理
auth/         会话与拦截器：Bearer Token → 数据库会话 → Principle
util/         统一响应体、业务异常、全局异常处理、订单号生成
```

DDD 的边界只做到"层"，没有过度拆聚合——这是一个 6 张主表的业务，拆太细反而增加沟通成本。

## 3. 数据模型

### 3.1 实体关系

```
sys_user 1───n print_order n───1 stored_file
                  │
                  ├──1───1 print_task        （一单一条任务，补打复用同一条）
                  └──1───n refund_record     （整单退款，一般 0~1 条）

admin_user      → 管理端账号（BCrypt）
user_session    → 会话（USER/ADMIN 共用表，token 只存 SHA-256）
sms_code        → 验证码（只存 SHA-256，含尝试次数与来源 IP）
price_config    → 单行配置（id=1），在线改价
audit_log       → 管理端敏感操作留痕
```

### 3.2 表说明

| 表 | 用途 | 关键设计 |
|---|---|---|
| `sys_user` | 打印用户，手机号即账号 | `uk_user_phone` 唯一；`status` 支持封禁 |
| `admin_user` | 管理员 | 只存 `password_hash`（BCrypt），不存明文 |
| `user_session` | 登录会话 | 主键是 token 的 SHA-256，**库泄露也无法直接冒用**；`expires_at` + `last_seen_at` 双重超时 |
| `sms_code` | 短信验证码 | 只存哈希；`attempts` 限错 5 次；按手机号/IP 小时配额 |
| `stored_file` | 待打印文件 | `storage_path` 原始件、`print_path` 实际送打印机件、`page_source` 区分真实/估算页数 |
| `price_config` | 收费标准 | 四档单价 + 双面系数 + 每单最低消费 |
| `print_order` | 订单 | 金额、页数、状态、支付渠道、`expire_at`、`terminal_id`、退款字段 |
| `print_task` | 打印任务 | `agent_id` 领取者、`retry_count`、`deadline_at`（僵尸回收）、`actual_pages` |
| `refund_record` | 退款流水 | 渠道退款单号、操作人、失败原因 |
| `audit_log` | 审计日志 | 改价/退款/补打/封禁/改口令全留痕（谁、何时、从哪个 IP、改了什么） |

### 3.3 关键索引

| 索引 | 作用 |
|---|---|
| `print_order.uk_order_no` | 订单号唯一，回调幂等的基础 |
| `print_order.idx_order_status_created` | 管理端按状态分页 |
| `print_order.idx_order_phone` | 按手机号检索 |
| `print_task.idx_task_status_created` | 助手领取候选扫描 |
| `print_task.idx_task_deadline` | 超时回收扫描 |
| `refund_record.idx_refund_order` | 订单退款流水查询 |
| `audit_log.idx_audit_created` | 审计倒序分页 |

## 4. 核心流程

### 4.1 下单与计价

```
用户上传文件
  → 魔数校验（%PDF / PK / 图片头 / OLE 头，不信任扩展名）
  → 大小与页数上限校验（默认 100MB / 500 页）
  → Office 文档：LibreOffice headless 转 PDF（每次独立 UserInstallation，避免并发锁）
  → PDFBox 统计真实页数，写入 stored_file.page_count / page_source=REAL
用户确认参数（份数、彩色、单双面、纸张）
  → 后端按 price_config 计算：
      总价 = 单价(色彩×纸张) × 页数 × 份数 × (双面 ? 系数 : 1)，再与最低消费取大
  → 生成订单号（PS + yyyyMMddHHmmss + 6 位随机），写入 expire_at = now + 10min
```

**为什么不信任前端算价**：任何前端算出来的价格都可以被改。后端只接受"参数"，金额永远由服务端重算。

### 4.2 支付（支付宝 / 微信）

```
POST /api/orders/{orderNo}/pay
  → 校验订单归属、状态（CREATED/PAYING）、是否已过期
  → 调用渠道 precreate（支付宝当面付 / 微信 Native）
       · 金额、商品名、超时时间（timeout_express / time_expire）由服务端填
  → 返回二维码内容给前端渲染，订单置为 PAYING
用户扫码支付
  → 渠道异步通知 → /api/pay/notify/{alipay|wechat}
  → 验签（支付宝 RSA2 + app_id；微信 SHA256-RSA2048 + 平台证书序列号 + 5 分钟重放窗口）
  → 解密（微信 AES-256-GCM）
  → 校验收款方（支付宝 seller_id / 微信 mchid + appid）
  → 校验金额（与订单 amount 逐分比对）
  → 加行锁（SELECT ... FOR UPDATE）后推进状态，重复通知直接幂等返回
```

三个校验缺一不可：

| 校验 | 如果不做会怎样 |
|---|---|
| 签名 | 任何人可以伪造"支付成功"通知，白打 |
| 收款方 | 有人把自己的商户号填进回调，钱进他口袋而系统照样出纸 |
| 金额 | 用 0.01 元的通知核销 50 元的订单 |

### 4.3 打印

```
打印助手（每 3 秒）
  → POST /api/agent/tasks/claim {agentId, terminalId}
      · 后端取候选：PENDING 且（terminal_id 为空 或 = 本终端）
      · 对每个候选执行条件更新：
          UPDATE print_task SET status='PRINTING', agent_id=?, deadline_at=?
          WHERE id=? AND status='PENDING'
      · 受影响行数 = 1 才算领到，否则换下一个候选
  → GET /api/agent/tasks/{taskId}/file?agentId=xxx   （只能下自己任务的 PDF）
  → SumatraPDF -print-to <printer> -print-settings "2x,duplexlong,mono,paper=A4"
  → 回查系统打印队列（Win32 EnumJobs / lpstat）
      · 任务出现 → 状态无异常 → 从队列消失 = 真正打印完成
      · 出现缺纸/脱机/卡纸/驱动报错并持续超过宽限期 = 判定失败
  → POST /api/agent/tasks/{taskId}/status {status, actualPages, failReason}
```

**为什么必须回查队列**：打印命令退出码为 0 只代表"文件已交给驱动"，缺纸、脱机、卡纸都在之后才发生。只信退出码，用户付了钱、纸没出来，系统却显示"已完成"——这是自助打印最常见的投诉来源。

### 4.4 退款与补偿

| 触发场景 | 行为 |
|---|---|
| 用户取消未支付订单 | 调渠道关单释放二维码，订单置 `CANCELLED` |
| 超时未支付（定时任务每分钟） | 同上，置 `EXPIRED`；若此时收到支付成功通知（用户卡在最后一秒），**入账后立即自动退款** |
| 打印失败（助手回传 FAILED） | 订单 `PRINT_FAILED` → 自动整单退款 → `REFUNDED` |
| 任务超时未回传 | 重排重试（默认 2 次），超限则判失败并自动退款 |
| 管理员手工退款 | 整单原路退回，写退款流水与审计日志 |

退款实现为三段式，避免"在事务里做 HTTP 调用"这种典型错误：

```
① claim  （REQUIRES_NEW）条件更新：NONE → PROCESSING，抢到才继续
② 调渠道（无事务、无行锁）        ← HTTP 慢不影响数据库
③ finish（REQUIRES_NEW）写流水 + 置 SUCCESS/FAILED
```

## 5. 状态机

### 5.1 订单

```
                 ┌───────────── cancel/expire ─────────────┐
                 ▼                                         │
 CREATED ──pay──▶ PAYING ──notify──▶ PAID ──claim──▶ PRINTING ──ok──▶ PRINTED
    │                │                 │                  │
    │                │                 │                  └──fail──▶ PRINT_FAILED
    │                │                 │                                     │
    └────────────────┴─────────────────┴──────── 退款 ──▶ REFUNDING ──▶ REFUNDED
                                                     （打印失败自动；管理员手工）
```

不变式：

- 只有 `CREATED` / `PAYING` 能发起支付；`EXPIRED` / `CANCELLED` 收到支付成功通知 → 入账后立即退款，**不会出纸**。
- `PAID` 之后金额与规格冻结，改价只影响新订单。
- `REFUNDED` 为终态，禁止补打。

### 5.2 打印任务

```
PENDING ──claim(条件更新)──▶ PRINTING ──SUCCESS──▶ SUCCESS
   ▲                            │
   └── 超时回收（retry+1）────────┤
                                └── 重试超限 / 助手回传失败 ──▶ FAILED
```

### 5.3 退款

```
NONE ──claim（条件更新）──▶ PROCESSING ──渠道返回──▶ SUCCESS / FAILED
```

## 6. 关键设计决策

### 6.1 并发领取任务：条件更新而非"先查后改"

早期实现是"查到就改"，8 个助手同时轮询会让同一任务被打印 8 份。现在改为：

```java
update PrintTask t set status=PRINTING, agentId=:agentId ...
where t.id=:id and t.status=PENDING
```

数据库行锁保证只有一个事务能把 `PENDING` 改成 `PRINTING`，`affectedRows==1` 才算领到。已用 8 线程并发测试验证：**最多 1 个成功**。

### 6.2 支付回调幂等 + 防重复入账

- 订单号唯一索引 + 行锁（`findByOrderNoForUpdate`）。
- 状态机只允许单向推进，重复通知命中"已经是 PAID"分支直接返回成功（渠道要求 200）。
- 金额、渠道、收款方三重校验（见 4.2）。

### 6.3 真实页数计费

页数是计价因子，估算会导致**多收或少收**。因此：

- Office 文档一律服务端转 PDF 后按 PDF 页数计费；转换失败默认拒单（`CONVERT_ALLOW_ESTIMATE=false`）。
- 页数来源写入 `page_source`，管理端与订单详情中显式标注 `REAL` / `ESTIMATE`。
- 预留"用户确认页数"环节：前端展示服务端算出的页数，用户确认后才下单。

### 6.4 终端绑定

每台打印电脑有自己的 `terminalId`（页面 `?t=T01`）。下单时写入订单，助手领取时按同值过滤。这样"在 A 楼下的单"不会在 B 楼出纸。未绑定终端的订单（`terminal_id` 为空）任何助手都能领，便于单点部署。

### 6.5 会话安全

| 设计 | 原因 |
|---|---|
| Token 只存 SHA-256 | 数据库被拖走也拿不到可用凭证 |
| 绝对过期 12h + 空闲 15min | 公共电脑上用户忘记退出是最常见的风险 |
| 前端空闲倒计时提示 | 让用户知道"再不动就退出"，而不是突然被踢 |
| 封禁用户立即删会话 | 处置要即时生效，不能等到下次登录 |
| 助手密钥常量时间比较 | 避免通过响应时间逐字节猜 token |

### 6.6 限流与防刷

- 验证码：同手机号 60 秒冷却、每小时 10 条；同 IP 每小时 30 条；验证失败 5 次作废。
- 管理端登录同样走会话机制，登录写审计。
- 订单支付超时 10 分钟，二维码随之失效，避免二维码被拍照后长期可用。

### 6.7 上传安全

| 风险 | 对策 |
|---|---|
| 上传可执行文件并诱导他人运行 | 白名单扩展名 + **魔数校验**（改扩展名无效）+ 落盘不放在 Web 根目录 + 下载强制 `Content-Disposition: attachment` |
| 超大文件打满磁盘 | 单文件 100MB、Nginx `client_max_body_size` 同步限制 |
| 文件长期堆积 | 定时任务按保留期（默认 7 天）清理，仍被未完结订单引用的跳过 |
| 越权下载他人文件 | 预览与下载都校验归属；助手侧按 `taskId + agentId` 授权，不再暴露可枚举的 `fileId` 下载口 |

### 6.8 XSS

模拟支付页会把 `orderNo` 回显到 HTML。所有动态内容统一 HTML 转义，且页面不含内联脚本。已用 `orderNo=<script>alert(1)</script>` 做过回归验证。

### 6.9 审计

改价、退款、补打、封禁、改口令都会写 `audit_log`（操作人、对象、详情、IP、时间）。写日志失败不影响主流程（try-catch + 告警日志），避免"审计失败导致业务失败"。

## 9. 安全设计汇总

| 威胁 | 对策 | 验证 |
|---|---|---|
| 未付款白打 | 模拟支付需本人且订单处于支付中；真实模式无任何旁路 | 攻击复测 D 组 4 项 |
| 伪造支付回调 | RSA2 / 平台证书验签 + 重放窗口 | 代码审查 + 单测 |
| 换收款方 / 少付 | `seller_id`、`mchid`、`amount` 三重校验 | 单测 `PaymentFlowTest` |
| 并发重复打印 | 条件更新 + 行锁 | 8 线程并发测试 |
| 越权看/打印他人文件 | 归属校验 + 按任务授权下载 | 攻击复测 D/E 组 |
| 短信轰炸 | 冷却 + 手机号/IP 双配额 + 尝试次数上限 | 单测 `SecurityRegressionTest` |
| XSS | HTML 转义 | 攻击复测 H 组 |
| 会话劫持残留 | Token 哈希存储 + 空闲超时 + 可吊销 | 攻击复测 F 组（封禁即踢出） |
| 口令泄露 | BCrypt + 不在仓库与日志中出现 | 代码审查 |
| 审计空白 | 敏感操作全留痕 | 攻击复测 F 组 |

## 10. 性能与容量

| 指标 | 估算 |
|---|---|
| 单笔下单（含 Office 转换） | 100 页 Word ≈ 2~4s（LibreOffice 启动占大头） |
| 单笔下单（PDF/图片） | < 200ms |
| 支付回调处理 | < 50ms（一次行锁 + 两次 update） |
| 任务领取 | < 20ms，单条 SQL 条件更新 |
| 单机并发 | 园区规模（同时 < 50 人在线）绰绰有余；Hikari 池 15 已足够 |
| 存储 | 每单平均 2~5MB，7 天保留期下 1000 单/天 ≈ 35GB，建议独立数据盘 |

瓶颈与对策：

- **LibreOffice 转换**是 CPU 密集型，与 Web 请求同机时建议限制并发上传或单独部署转换节点（`DocumentConverter` 已是独立类，可平移）。
- 文件存本地磁盘，扩容靠换盘；如需多机部署，把 `FileService` 的存储实现换成对象存储即可（接口已隔离）。

## 12. 已知限制与后续演进

| 限制 | 说明 | 建议 |
|---|---|---|
| 单机部署 | 文件存本地、定时任务未做分布式选主 | 多实例前先把文件迁对象存储，定时任务加 ShedLock |
| 无对账文件核销 | 目前依赖实时回调 + 主动查询兜底 | 接入支付宝/微信对账单下载，做 T+1 自动对账 |
| 打印机型号适配 | SumatraPDF 对纸张/双面的支持取决于驱动 | 上线前在目标机型上按 `docs/部署与使用说明书.md` 的验收清单逐项试打 |
| 无电子发票 | 招标未要求 | 若需要，可接第三方开票平台 |
| 无小程序/H5 适配 | 当前按公共电脑横屏设计 | 移动端可作为下一版本 |
